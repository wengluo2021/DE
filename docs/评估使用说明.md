**What this part is doing.**

A first produces 30 questions and writes the reference answers, key facts, and source-text evidence. The program has the system answer each once under the four chunking conditions f400, s400, f800, and s800, saving 120 records in total. The four groups use the same questions, corpus, index version, and generation parameters. The standard answers are kept only for evaluation and scoring and are not sent to the model.

Your scoring work is to read the answers the system has already generated and judge them against A's standard answers and this round's source-text evidence. You do not need to write questions for A, and you cannot modify the standard answers to accommodate the system output.

Each run_id represents one experiment, and each task_id represents a background task; the same question has one record, an independent Q&A number, and a score under each condition. A task being completed only means the 120 items have been processed; you still need to check errors; failed questions are also retained.

```powershell

$env:DERAG_ENV_FILE='../.private/school-llm.env'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8765
```

Start only one worker, without reload. By default it reads the project .env; you can also set DERAG_ENV_FILE to the path of an existing local env before starting. For the location of the school API private configuration, see the outer workspace document 《学校LLM_API对接文档.md》.

Once the formal prerequisites are in place, submit in another terminal:

```powershell
.\.venv\Scripts\python.exe -m scripts.run_eval --config config/experiment.formal-a.json --base-url http://127.0.0.1:8765
```

The CLI first checks the actual local and service configuration, then only submits, polls, and exports over HTTP; it does not start another worker or take over the database. By default it exports to data/runs/client-random-number/; you can use --output-dir to choose a directory that does not yet exist. The JSON retains complete records, and each CSV row is one question under one condition, including failed items.

The terminal first displays run_id/task_id; please keep them. The default wait limit is 7200 seconds, adjustable with --timeout. A polling timeout does not cancel the background experiment; do not resubmit just because you did not wait long enough.

Reading existing results is allowed even when the generation service is not currently ready, but the local and saved configurations must still match. When a background task fails, also export the saved records; the CLI exits with a non-zero status.

**How to score.**

M4 has been wired into the scoring page: open /evaluation, select an experiment, click "View / Score" for a given condition and question, fill in the actual reviewer, the answer/refusal judgment, and the per-claim reasons, then save. After viewing the source text you can return to scoring; drafts exist only in the current page's memory, so save before refreshing. Synthetic tests cannot be used as formal scoring.

You can also open http://127.0.0.1:8765/docs直接操作API。先GET /api/evaluations to find experiments, then GET /api/evaluations/{run_id} to view per-question results, gold evidence, citations for this run, and the number of items pending review.

PATCH /api/evaluations/{run_id}/cases/{case_id}?condition=s400 modifies only that question under that condition:

```json
{
  "answer_grade": "correct",
  "claim_reviews": [
    {"claim_index": 0, "supported": true, "reason": "state how the quoted source text supports this claim"}
  ],
  "refusal_correct": null,
  "reviewer": "fill in the actual reviewer",
  "notes": "state which necessary facts were checked, and what is missing or wrong"
}
```

This is only a field example, not a pre-assigned score for a formal question. claim_index starts at 0 and refers to the position of the claim in this answer; citation number n starts at 1 and is bound to this run's ask_id. Review time is recorded automatically, and modifications keep a history. PATCH updates only the submitted fields; an explicit null can withdraw an item pending verification.

| Review target | How to judge |
| --- | --- |
| Answerable question answer | correct: the necessary facts are correct and complete; partial: only part is answered correctly; wrong: incorrect or an erroneous refusal. Only correct counts toward answer accuracy. |
| Each factual claim | Read the evidence from this run that the claim actually cites, judge whether it supports the conclusion, and write a reason. Do not mark true just because the number exists. |
| Questions that should be refused | answer_grade is null; fill in refusal_correct; generating an answer cannot be marked as a correct refusal. If factual claims appear, still verify the citations. |
| Technical failure | Keep the error, do not fabricate a generated answer, and do not treat it as a completed answer that can be manually scored. |

Automatic metrics cannot be overridden through the scoring API; invalid conditions, out-of-range claims, and scores that contradict the question type will be rejected.

**How to read the metrics.**

- hit@1/hit@5: the union of intervals of the first k chunks within the same document must fully cover the gold evidence; half a sentence does not count. For multiple evidence items, report any and all separately; positions are not merged across documents. The denominator is fixed at 24.
- Answer accuracy = correct/24; refusal accuracy = correct refusals/6. Failures do not remove questions; partial, wrong, erroneous refusals, and errors are listed separately.
- Citation accuracy = number of claims manually confirmed as supported by the cited evidence / number of factual claims with citations. When unverified, pending is not 0 and value is null; with no citations the denominator is also null. The number of failed questions is listed separately; do not assume how many valid claims are in a failed request.
- Each ratio stores numerator, denominator, pending, and failed_cases. A hit may still have occurred even if later generation failed, so failed cases cannot be subtracted directly from the hit denominator.
- The median latency summarizes only successful results; context character counts and available token counts are stored separately. Tokens distinguish known/unknown attempts and include repair retries; unknown does not masquerade as 0 cost.
- review_complete means there are no items pending review; finalizable additionally requires the run to be complete and no model drift. Errors must still be checked. formal_results for synthetic test results is always false.
- paired_cases places the four sets of results for the same case_id together, making it easier to analyze which chunking method is better and why it fails.

**Export and shutdown.**

GET /api/evaluations/{run_id}/export?format=json or format=csv only reads saved results and does not re-retrieve or call the model. CSV prefixes standalone text that spreadsheet software might treat as a formula; the exact original text remains in the nested JSON and the JSON export.

Each question is registered first, evidence is saved after retrieval, and progress is saved on each generation attempt. After a hard shutdown, the next service start marks unfinished questions and tasks as PROCESS_INTERRUPTED; completed answers and scores are retained, and paid requests are not retried automatically. To rerun, create a new experiment and keep the old run_id as a failure record. A normal exit waits for its own workers to finish; for formal experiments, try to keep the computer running, and shut down only after completion and export.
