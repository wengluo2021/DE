# P800 父子分块扩展（Small-to-Big Retrieval）

> 状态：代码骨架、单元测试和 retrieval-only 评测脚本已完成；**真实模型建库和 P800 评测尚未运行**。本文中的 625 / 2,343 / 2,099 是直接用冻结语料和现有 S800 分块器算出的确定数字，不是模型实验结果。

## 1. 要回答的问题

现有四组实验中，S800 在本轮最好：

| 方案 | Hit@5-all | 答案完整正确 | 引用支持 |
|---|---:|---:|---:|
| F400 | 4/24 | 6/24 | 28/35 |
| S400 | 6/24 | 9/24 | 33/35 |
| F800 | 10/24 | 10/24 | 43/46 |
| S800 | 13/24 | 14/24 | 50/50 |

但 S800 仍有 11 道可答题没有做到 Top-5 完整证据覆盖。离线检查发现：

- 24 道可答题中，有 **20 道**的全部标准证据都能分别完整落在某个 S800 父块内部；
- 实际 Top-5 只完整覆盖 **13 道**；
- 至少 **7 道题**属于“正确父块确实存在，但没被排进前五”。

因此，这个扩展不再增加一个 400/800 档位，而是问：

> **如果父块仍然是 S800，但用更小的子块来做向量匹配，能不能把正确的 S800 父块排进 Top-5？**

这正好对应 small-to-big / parent-child retrieval：**小子块负责找，大父块负责给模型读**。

## 2. 方法

```text
父块：S800 结构块，625 个，≤800 字符
      [---------- 800 chars ----------]
子块：父块内按句边界切，默认 250 字符
      ├─ 250 ─┤├─ 250 ─┤├─ 250 ─┤ ...

建库：只给子块做 BGE-M3 embedding，存入独立 Chroma collection
检索：问题 → 子块 Top-50
      → 按 parent_id 分组去重
      → 父块得分 = 该父块下最高子块得分
      → 取 Top-5 个不同父块
生成：LLM 仍然看 5 个完整父块，不看 250 字子块
引用：引用父块；matched_child_* 字段记录命中的子块，便于高亮
```

### 2.1 为什么父块用 S800，而不是完整法条

- S800 父块 ≤800 字符，和现有契约一致；
- P800 与 S800 的**证据单元完全相同**，所以 Hit@5、上下文字符数可以直接比较；
- 唯一变化是“检索粒度”，这是干净的对照实验；
- 完整法条可能超过 800 字符，会破坏上下文可比性，也会让引用/契约变复杂。

如果 P800 有效，后续可以再讨论“父块=完整法条”的变体；第一版不建议。

### 2.2 子块规则

- 在父块内部按句末标点和换行切分；
- 相邻句子贪心打包到 `child_chars`（默认 250）；
- 单个句子超过 250 才硬切；
- 不重叠，子块拼接严格等于父块；
- 长度小于 `min_child_chars`（默认 40）的片段保留在父块中，但标记 `indexable=false`，不写入 Chroma，避免标题/空白变成噪声向量。

### 2.3 冻结语料上的实际数字

用 `data/formal_corpus/processed/*.json` 和现有 `chunks_for_condition(doc, "s800")` 直接计算：

| 项目 | 数值 |
|---|---:|
| S800 父块 | 625 |
| 全部子块 span | 2,343 |
| 实际索引子块（≥40 字符） | 2,099 |
| 跳过的短片段 | 244 |
| 至少有一个索引子块的父块 | 620 / 625 |
| 完全没有索引子块的父块 | 5 |
| 索引子块平均每父块 | 3.36 |
| 索引子块长度中位数 | 199 |
| 索引子块最大长度 | 250 |

被跳过的 244 个短片段中，有 5 个父块整块都小于 40 字符，分别是 `CHAPTER II`、`CHAPTER III`、`CHAPTER 2`、`CHAPTER 4` 和 `Section 1` 这类章节标题。它们不会进入子块索引；父块文本仍保留在 `parents.jsonl` 里。当前 gold 证据最短 68 字符，不依赖这些章节标题。`manifest.json` 的 `counts.unindexed_parent_ids` 会列出这 5 个 ID，便于报告时解释 620/625。

## 4. 运行

以下命令都在项目根目录、使用项目自己的 `.venv` 执行。

### 4.1 先做不加载模型的 dry run

```powershell
& '.\.venv\Scripts\python.exe' -m scripts.build_p800 `
  --config config/experiment.formal-a.json `
  --dry-run
```

它只读取 A 的冻结正文、重算 S800 父块、写 `parents.jsonl` 和 `children.jsonl`，并打印父块/子块计数。**不会加载 BGE-M3，也不会写 Chroma。**

### 4.2 建 P800 子块索引

```powershell
& '.\.venv\Scripts\python.exe' -m scripts.build_p800 `
  --config config/experiment.formal-a.json
```

- 只编码约 2,099 个子块，不重建 F400/S400/F800/S800；
- 模型缺失时先按项目说明运行 `scripts.fetch_embedding`；
- Windows 路径过长时按项目现有约定缩短 `DERAG_DATA_DIR` 或数据目录；
- 输出：
  - `parents.jsonl`
  - `children.jsonl`
  - `manifest.json`
  - `chroma/<index_version>/`

### 4.3 retrieval-only 评测

```powershell
& '.\.venv\Scripts\python.exe' -m scripts.eval_p800 `
  --config config/experiment.formal-a.json `
  --baseline exports/20261120-232137-eval-ca61c0c0/evaluation.json
```

- 不调用 LLM，不需要 API key；
- 30 题中只有 24 道可答题参与 hit 指标；6 道拒答题仍写入 JSON，但 hit 为 null；
- 默认 `--candidate-k 50`：先取 50 个子块，再去重成父块；
- 输出到 `data/formal_corpus/extension/p800/eval-<UTC时间>/`：
  - `p800-eval.json`：完整逐题记录；
  - `summary.json`：汇总；
  - `p800-cases.csv`：逐题 P800 与 S800 对照；
  - `p800-vs-s800.csv`：同一份数据的精简表。

### 4.4 只跑前几题做 smoke test

```powershell
& '.\.venv\Scripts\python.exe' -m scripts.eval_p800 `
  --config config/experiment.formal-a.json `
  --limit 3
```

## 5. 指标口径

| 指标 | 含义 |
|---|---|
| `p800.hit_at_1/5.any` | Top-1/5 父块的原文区间并集，至少覆盖一段标注证据 |
| `p800.hit_at_1/5.all` | Top-1/5 父块覆盖全部标注证据；和现有 `Hit@k` 同一口径 |
| `p800.candidate.any/all` | Top-50 子块去重后的**所有父块**能否覆盖证据；这是候选池的诊断上限，不是最终成绩 |
| `p800.context_chars` | Top-5 父块的字符总数；与 S800 同粒度，可直接比较 |
| `p800.retrieve_ms` | 问题编码 + 子块查询 + 父块聚合的总耗时 |
| `p800.parent_count` | 候选池去重后的父块数 |
| `p800.child_count` | 实际返回的子块数 |
| `delta_hit5_all` | P800 减 S800：+1 表示这题从“未完整覆盖”变成“完整覆盖” |
| `delta_context_chars` | P800 上下文减 S800 上下文；正数表示 P800 用了更多字符 |

**怎么读 `candidate`：**

- 如果 `candidate.all` 很高、`hit_at_5.all` 不高：正确父块已经在候选池里，问题在父块排序/聚合；
- 如果 `candidate.all` 也低：子块匹配本身没找到，可能需要换子块大小或换检索方式；
- 如果 `candidate.all` 高但 P800 仍不如 S800：说明“子块检索 + 父块排序”没有把优势转化出来，要检查打分方式（当前用最高子块分，不用求和）。

## 7. 公平性与限制

- **同语料、同 embedding、同父块、同 Top-5、同 prompt/模型**（如果后续做生成）；
- 只改变检索粒度：S800 直接用父块向量查 Top-5；P800 用子块查 Top-50 再回溯父块；
- 父块完全一致，所以这不是“把块变大”带来的虚高；
- 子块大小 250、`min_child_chars=40`、`candidate-k=50` 是**预先固定**的，不要用 30 道测试题反复调；
- 30 题样本小，结论只适用于本轮冻结语料；
- 5 个章标题父块没有子块索引，属于已知覆盖缺口；
- 仍有一道题的标准证据被 S800 父块边界切断，P800 父块仍用 S800，所以它救不了这道题；
- 当前没有做生成，不能把 retrieval-only 的结果说成“答案正确率提升”。
